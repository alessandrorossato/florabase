# Cross-domain bulk operations — proposal for separate approval

28 October 2026. Audit of the current API/domain workflows, not an implementation promise.
No new bulk endpoint or mutation was added in this refinement. A single-record PUT or a loop of
single-record requests is **not** an audited bulk contract.

## Supported today

**Move to Location** (`POST /api/v1/bulk/location/preview` and `/apply`) already supports explicit
SeedLot, Sowing, Plant, PlantGroup and managed Harvest inventory references, maximum 100.
Only active records qualify, and the destination must allow each selected domain's physical scope.
The server previews every move/no-op/conflict. Apply locks/re-reads records and the target,
compares their timestamps, and rejects stale/ineligible selections as one transaction. No partial
success. Plant/group moves create authoritative movement Events; SeedLot/Sowing/stored-material
moves retain their existing owning-domain assignments. No movement History is inferred from
`updated_at`. Historical Harvest records themselves are not movable stored inventory.

The existing Labels composer accepts SeedLots, Plants, PlantGroups and stored material. Preparing
multiple labels is a read/print operation with its own copies, quantity and page geometry; it is
not permission to mutate those records. Connecting directory selection to this existing composer
could be a separate UI increment, with no new generalized mutation backend.

of existing writes. First reuse supported Location moves and consider Labels handoff; then approve
one bounded metadata/sourcing increment with its own server contract and acceptance tests.
